## 1. Basic parent-child hierarchy

Indenting a table under another automatically creates a foreign key from child to parent. The child table gets a `<parent>_id` column and an index on that column.

**Input:**

```expresql
departments /insert 2
  name /nn
  location
  employees /insert 4
    name /nn vc50
    email /lower
    salary num(10,2)
    date hired

emp_v = departments employees
```

**Key generated DDL:**

```sql
create table departments (
    id          number generated by default on null as identity
                constraint departments_id_pk primary key,
    name        varchar2(255 char) not null,
    location    varchar2(4000 char)
);

create table employees (
    id               number generated by default on null as identity
                     constraint employees_id_pk primary key,
    department_id    number
                     constraint employees_department_id_fk
                     references departments,
    name             varchar2(50 char) not null,
    email            varchar2(255 char),
    salary           number(10,2),
    date_hired       date
);

create index employees_i1 on employees (department_id);

-- /lower generates a BEFORE INSERT OR UPDATE trigger
create or replace trigger employees_bi
    before insert on employees for each row
begin
    :new.email := lower(:new.email);
end employees_bi;
/

-- Join view via "name = t1 t2" syntax
create or replace view emp_v as
select departments.id        department_id,
       departments.name      department_name,
       departments.location  location,
       employees.id          employee_id,
       employees.name        employee_name,
       employees.email       email,
       employees.salary      salary,
       employees.date_hired  date_hired
from   departments
left join employees on employees.department_id = departments.id;
```

## 2. Audit columns and APEX integration

`auditcols: yes` adds four audit columns to every table. The `apex: yes` setting switches the trigger to use `coalesce(sys_context('APEX$SESSION','APP_USER'), user)` instead of just `user`.

**Input:**

```expresql
projects
  name vc200 /nn
  status /check OPEN,ACTIVE,CLOSED /nn
  budget num(12,2)

# settings = { auditcols: yes, apex: yes }
```

**Key generated DDL:**

```sql
create table projects (
    id            number generated by default on null as identity
                  constraint projects_id_pk primary key,
    name          varchar2(200 char) not null,
    status        varchar2(4000 char) not null
                  constraint projects_status_ck check (status in ('OPEN','ACTIVE','CLOSED')),
    budget        number(12,2),
    created       date,
    created_by    varchar2(255 char),
    updated       date,
    updated_by    varchar2(255 char)
);

create or replace trigger projects_biu
    before insert or update on projects for each row
begin
    if inserting then
        :new.created    := sysdate;
        :new.created_by := coalesce(sys_context('APEX$SESSION','APP_USER'), user);
    end if;
    :new.updated    := sysdate;
    :new.updated_by := coalesce(sys_context('APEX$SESSION','APP_USER'), user);
end projects_biu;
/
```

## 3. Column prefix and composite primary key

`/colprefix` adds a short prefix to every column in a table, reducing name collisions when joining. A table-level `/pk` builds a composite primary key from the listed columns (here used alongside manual `/pk` directives on columns).

**Input:**

```expresql
order_lines /colprefix ol
  order_id   /fk orders /nn
  product_id /fk products /nn
  quantity   num /nn
  unit_price num(10,2) /nn
  /pk order_id product_id
```

**Key generated DDL:**

```sql
create table order_lines (
    ol_order_id      number not null
                     constraint order_lines_ol_order_id_fk
                     references orders,
    ol_product_id    number not null
                     constraint order_lines_ol_product_id_fk
                     references products,
    ol_quantity      number not null,
    ol_unit_price    number(10,2) not null,
    constraint order_lines_pk primary key (ol_order_id, ol_product_id)
);
```

The underscore separator is added automatically if not included in the prefix value.

## 4. Foreign key to a table outside the model

`/fk <table>` creates a foreign key to any table — it does not need to be defined in the current QSQL script. This is useful when referencing lookup tables maintained separately.

**Input:**

```expresql
invoices
  customer_id /fk customers /nn
  currency_code vc3 /fk ref_currencies /nn
  total num(14,2) /nn
  status /check DRAFT,ISSUED,PAID,VOID /nn
```

**Key generated DDL:**

```sql
create table invoices (
    id               number generated by default on null as identity
                     constraint invoices_id_pk primary key,
    customer_id      number not null
                     constraint invoices_customer_id_fk
                     references customers,
    currency_code    varchar2(3 char) not null
                     constraint invoices_currency_code_fk
                     references ref_currencies,
    total            number(14,2) not null,
    status           varchar2(4000 char) not null
                     constraint invoices_status_ck
                     check (status in ('DRAFT','ISSUED','PAID','VOID'))
);
```

If the referenced table does not exist at parse time ExpreSQL still generates the constraint; the FK will validate at install time.

## 5. Star schema (fact + dimension tables)

The `>` prefix in front of a child table name reverses the FK direction: instead of the child carrying a FK to the parent, the **fact** table carries FKs to the **dimension** tables. This is the standard star-schema pattern.

**Input:**

```expresql
sales /insert 2
  quantity
  > products /insert 1
    name
    category vc100
  > customers /insert 1
    first name
    country vc2

# settings = { pk: identityDataType, semantics: CHAR }
```

**Key generated DDL:**

```sql
-- Dimension tables have their own PKs
create table customers (
    id           number generated by default on null as identity
                 constraint customers_id_pk primary key,
    first_name   varchar2(4000 char),
    country      varchar2(2 char)
);

create table products (
    id          number generated by default on null as identity
                constraint products_id_pk primary key,
    name        varchar2(255 char),
    category    varchar2(100 char)
);

-- Fact table carries the FKs to both dimensions
create table sales (
    id              number generated by default on null as identity
                    constraint sales_id_pk primary key,
    product_id      number
                    constraint sales_product_id_fk references products,
    customers_id    number
                    constraint sales_customers_id_fk references customers,
    quantity        number
);

create index sales_i1 on sales (product_id);
create index sales_i2 on sales (customers_id);
```

## 6. JSON Duality Views (23ai+)

`dv <view_name> <root_table> <child_table>` generates a JSON Relational Duality View. The root table is the top-level JSON document; nested tables are embedded as arrays based on their FK relationships.

**Input:**

```expresql
departments
  name vc200 /nn
  employees
    first_name vc100 /nn
    last_name  vc100 /nn
    salary     num(10,2)

dv dept_emp_dv departments employees

# settings = { db: "23c" }
```

**Key generated DDL:**

```sql
create table departments (
    id      number generated by default on null as identity
            constraint departments_id_pk primary key,
    name    varchar2(200 char) not null
);

create table employees (
    id               number generated by default on null as identity
                     constraint employees_id_pk primary key,
    department_id    number
                     constraint employees_department_id_fk
                     references departments,
    first_name       varchar2(100 char) not null,
    last_name        varchar2(100 char) not null,
    salary           number(10,2)
);

create or replace json relational duality view dept_emp_dv as
departments @insert @update @delete {
    _id       : id,
    name      : name,
    employees : employees @insert @update @delete
    [{
        _id        : id,
        first_name : first_name,
        last_name  : last_name,
        salary     : salary
    }]
};
```

Each row in `departments` becomes a JSON document. The `employees` array is embedded and fully updateable via the duality view.

## 7. Multi-lingual columns with /trans

`/trans` on a column generates three objects: a shared `language` lookup table, a `<table>_trans` translation table (one row per parent row × language), and a `<table>_resolved` view that applies `COALESCE` to fall back to the base value when no translation exists.

**Input:**

```expresql
products
  name       vc200 /nn /trans
  description       /trans
  price      num(10,2)

# prefix: shop
```

**Key generated DDL (abbreviated):**

```sql
create table shop_products (
    id           number generated by default on null as identity
                 constraint shop_products_id_pk primary key,
    name         varchar2(200 char) not null,   -- base/fallback value
    description  varchar2(4000 char),           -- base/fallback value
    price        number(10,2)
);

-- Shared language table (one per schema)
create table shop_language (
    code           varchar2(5 char) not null
                   constraint shop_language_code_pk primary key,
    locale         varchar2(28 char) not null
                   constraint shop_language_locale_unq unique,
    name           varchar2(1024 char),
    native_name    varchar2(1024 char)
);

-- Translation table: trans_ prefix on translated columns
create table shop_products_trans (
    id               number generated by default on null as identity
                     constraint shop_products_trans_id_pk primary key,
    products_id      number not null,
    language_code    varchar2(5 char) not null,
    trans_name       varchar2(200 char),
    trans_description varchar2(4000 char),
    constraint shop_products_trans_uk unique (products_id, language_code)
);

-- Resolved view: LEFT JOIN with COALESCE fallback
create or replace view shop_products_resolved as
select k.id,
       coalesce(t.trans_name,        k.name)        as name,
       coalesce(t.trans_description, k.description) as description,
       k.price
from   shop_products k
left join shop_products_trans t
    on  t.products_id   = k.id
    and t.language_code = sys_context('APP_CTX', 'LANG');
```

## 8. Immutable table and temporal history

`/immutable` creates an append-only table by installing a trigger that raises an error on any UPDATE or DELETE. `/history` generates a shadow `_history` table and triggers that capture every row version with timestamp ranges.

**Input:**

```expresql
audit_log /immutable
  entity    vc128 /nn
  entity_id num /nn
  operation vc10 /nn
  payload   clob

contract_versions /history
  contract_id num /nn /fk contracts
  content     clob /nn
  version_num num /nn
```

**Key generated DDL:**

```sql
create table audit_log (
    id          number generated by default on null as identity
                constraint audit_log_id_pk primary key,
    entity      varchar2(128 char) not null,
    entity_id   number not null,
    operation   varchar2(10 char) not null,
    payload     clob
);

-- Trigger blocks any UPDATE or DELETE
create or replace trigger trg_audit_log_insertonly
    before update or delete on audit_log
begin
    raise_application_error(-20055, 'audit_log is immutable');
end;
/

create table contract_versions (
    id              number generated by default on null as identity
                    constraint contract_versions_id_pk primary key,
    contract_id     number not null
                    constraint contract_versions_contract_id_fk
                    references contracts,
    content         clob not null,
    version_num     number not null,
    valid_from      timestamp,
    valid_to        timestamp
);

-- History shadow table captures every row state
create table contract_versions_history (
    id              number,
    contract_id     number,
    content         clob,
    version_num     number,
    valid_from      timestamp,
    valid_to        timestamp,
    operation       varchar2(10 char),
    changed_by      varchar2(255 char),
    changed_on      timestamp
);
```

## 9. SODA document collection

`/soda` creates a table with the fixed schema required by Oracle SODA: a RAW(16) document ID, timestamps, a version string, and a BLOB column with a `IS JSON` check.

**Input:**

```expresql
sensor_readings /soda
events /soda /rest
```

**Key generated DDL:**

```sql
create table sensor_readings (
    id                varchar2(255 char)
                      constraint sensor_readings_id_pk primary key,
    created_on        timestamp,
    last_modified     timestamp,
    version           varchar2(255 char),
    json_document     blob
                      check (json_document is json)
);

create table events (
    id                varchar2(255 char)
                      constraint events_id_pk primary key,
    created_on        timestamp,
    last_modified     timestamp,
    version           varchar2(255 char),
    json_document     blob
                      check (json_document is json)
);

-- REST enablement for events
begin
    ords.enable_object(
        p_enabled      => true,
        p_schema       => sys_context('USERENV','CURRENT_SCHEMA'),
        p_object       => 'EVENTS',
        p_object_type  => 'TABLE',
        p_auto_rest_auth => false
    );
    commit;
end;
/
```

SODA tables are managed through the Oracle SODA API (Java, Python, REST) and are not meant to be queried relationally.

## 10. Flashback Data Archive

`/flashback` enables Flashback Data Archive on the table. An optional archive name can be specified; if omitted Oracle uses the default archive.

**Input:**

```expresql
salaries /flashback payroll_fda
  employee_id /fk employees /nn
  amount      num(12,2) /nn
  effective   date /nn

config_values /flashback
  key   vc100 /nn /unique
  value clob
```

**Key generated DDL:**

```sql
create table salaries (
    id             number generated by default on null as identity
                   constraint salaries_id_pk primary key,
    employee_id    number not null
                   constraint salaries_employee_id_fk references employees,
    amount         number(12,2) not null,
    effective      date not null
);

alter table salaries flashback archive payroll_fda;

create table config_values (
    id      number generated by default on null as identity
            constraint config_values_id_pk primary key,
    key     varchar2(100 char) not null
            constraint config_values_key_unq unique,
    value   clob
);

alter table config_values flashback archive;
```

Flashback Data Archive requires an archive configured by a DBA (`CREATE FLASHBACK ARCHIVE`). It retains all historical row versions for queries like `AS OF TIMESTAMP`.

## 11. Sample data generation: /insert, /values, /constant

`/insert N` generates N random INSERT rows per table. `/values` constrains the random pool for a specific column. `/constant` pins a column to a fixed value. `inserts: false` suppresses all INSERTs globally (useful for production DDL scripts).

**Input:**

```expresql
orders /insert 5
  customer_id num /nn /constant 42
  status      /values OPEN,PENDING,SHIPPED /nn
  region      vc20 /values EMEA,AMER,APAC
  total       num(10,2)

# inserts: true
```

**Key generated DDL (data portion):**

```sql
insert into orders (customer_id, status, region, total)
values (42, 'PENDING', 'APAC', 1847.23);

insert into orders (customer_id, status, region, total)
values (42, 'OPEN', 'EMEA', 392.10);

-- ... 3 more rows; customer_id always 42, status/region from the /values pools
```

To generate clean DDL without any INSERT statements:

```expresql
orders /insert 100   -- directive is ignored when inserts is false
  name vc100

# inserts: false
```

## 12. Oracle SQL Annotations

Curly-brace `{...}` syntax adds Oracle SQL annotations to tables, columns, and views. The special `DESCRIPTION` key also generates a `COMMENT ON` statement. The `GROUP` key registers an annotation group.

**Input:**

```expresql
employees {DESCRIPTION 'HR workforce table', Classification 'HR', GROUP 'PII'}
  name     vc200 /nn {DESCRIPTION 'Full legal name', Sensitivity 'Private'}
  email    vc200      {DESCRIPTION 'Work email address'}
  salary   num(12,2)  {Sensitivity 'Confidential'}
```

**Key generated DDL:**

```sql
create table employees (
    id        number generated by default on null as identity
              constraint employees_id_pk primary key,
    name      varchar2(200 char) not null
              annotations (DESCRIPTION 'Full legal name', Sensitivity 'Private'),
    email     varchar2(200 char)
              annotations (DESCRIPTION 'Work email address'),
    salary    number(12,2)
              annotations (Sensitivity 'Confidential')
)
annotations (DESCRIPTION 'HR workforce table', Classification 'HR', GROUP 'PII');

-- DESCRIPTION annotation also generates COMMENT ON
comment on table employees is 'HR workforce table';
comment on column employees.name  is 'Full legal name';
comment on column employees.email is 'Work email address';

-- GROUP annotation inserts into annotation group tables
insert into user_annotations_groups$ (group_name) values ('PII');
insert into user_annotations_group_members$ (group_name, object_name)
values ('PII', 'EMPLOYEES');
```

## 13. REST enablement with ORDS

`/rest` generates an `ords.enable_object` call to publish the table as a REST resource via Oracle REST Data Services.

**Input:**

```expresql
products /rest /insert 3
  name  vc200 /nn
  price num(10,2) /nn
  sku   vc50 /unique

categories /rest
  label vc100 /nn /unique
```

**Key generated DDL:**

```sql
create table products (
    id      number generated by default on null as identity
            constraint products_id_pk primary key,
    name    varchar2(200 char) not null,
    price   number(10,2) not null,
    sku     varchar2(50 char)
            constraint products_sku_unq unique
);

create table categories (
    id      number generated by default on null as identity
            constraint categories_id_pk primary key,
    label   varchar2(100 char) not null
            constraint categories_label_unq unique
);

-- REST enablement block (one per /rest table)
begin
    ords.enable_object(
        p_enabled        => true,
        p_schema         => sys_context('USERENV','CURRENT_SCHEMA'),
        p_object         => 'PRODUCTS',
        p_object_type    => 'TABLE',
        p_auto_rest_auth => false
    );
    commit;
end;
/
```

ORDS must be installed and configured in the database. After running the script, the table is accessible at `https://<host>/ords/<schema>/products/`.

## 14. Table API (TAPI) — simple and layered tiers

**Simple API** (`api: yes`): one `<table>_api` package with `get_row`, `insert_row`, `update_row`, `delete_row`.

**Layered API**: a stack of packages per table, selected by the tier argument on `/api`. No global setting needed — the tier is self-contained.

### Simple API

```expresql
products /api
  name  vc200 /nn
  price num(10,2)

# settings = { api: yes }
```

Generated: `products_api` — single package with four procedures.

### Layered API — all six tiers

```expresql
-- tier: lookup (app interface only)
-- generated: items_app
items /api lookup
  code  vc20 /nn
  label vc100 /nn

-- tier: lookup+hks
-- generated: categories_hks, categories_app
categories /api lookup+hks
  code  vc20 /nn
  label vc100 /nn

-- tier: service
-- generated: orders_svc, orders_app
-- _svc body embeds private DML (no _dal)
orders /api service
  customer_id num /nn
  total       num(12,2)

-- tier: service+hks
-- generated: invoices_hks, invoices_svc, invoices_app
invoices /api service+hks
  order_id num /nn
  amount   num(12,2)

-- tier: full  (no hook stubs)
-- generated: employees_dal, employees_svc, employees_app
employees /api full
  name  vc100 /nn
  email vc200 /nn

-- tier: full+hks  (default for bare /api)
-- generated: contracts_dal, contracts_hks, contracts_svc, contracts_app
contracts /api full+hks
  title      vc200 /nn
  row_version num /nn
```

Package name anatomy for `contracts` with no prefix:

| Package | Role |
| --- | --- |
| `contracts_dal` | Data Access Layer — raw DML (`get_by_id`, `insert_row`, `update_row`, `delete_row`) |
| `contracts_hks` | Hooks — override stubs (`validate`, `before_insert`, `after_insert`, …) |
| `contracts_svc` | Service — orchestrates DAL + hooks; public API (`create_rec`, `get`, `update_rec`, `delete_rec`) |
| `contracts_app` | Application interface — named-parameter wrappers over `_svc` |

## 15. Audit log chain (`/auditlog`)

`/auditlog` on a table generates an `<table>_aud` package that captures every DML event
in an audit log table via `PRAGMA AUTONOMOUS_TRANSACTION`. The audit record persists even
if the outer transaction rolls back.

**Requirements:** the audit log table must exist in the schema (or be defined in the same
QSQL input), and both tables must use a layered tier.

```expresql
-- 1. Define the audit log table (also gets layered API for querying)
app_audit_log /api full+hks
  entity     vc128 /nn
  entity_id  num   /nn
  operation  vc6   /nn
  old_values clob
  new_values clob

-- 2. Audited table — /auditlog names the log table (without prefix)
employees /api full+hks /auditlog app_audit_log
  name        vc100 /nn
  email       vc200 /nn /unique
  row_version num   /nn
```

**Generated packages for `employees`:**

| Package | Role |
| --- | --- |
| `employees_dal` | Raw DML |
| `employees_hks` | Business rule stubs |
| `employees_svc` | Orchestration; calls `employees_aud` after each DML |
| `employees_app` | Application interface |
| `employees_aud` | Autonomous-transaction audit writer |

The `employees_aud` package:

- declares `g_enabled boolean := true` — flip to `false` to suppress audit without code change
- contains a private `f_to_json` function that serialises the row to a JSON string
- `log_insert(p_row)`, `log_update(p_old_row, p_new_row)`, `log_delete(p_old_row)` delegate to a private `p_log` procedure that calls `app_audit_log_svc.create_rec` inside an autonomous transaction

> **Log table name:** `/auditlog` with no argument defaults to `app_audit_log`.
> Use the explicit form — `/auditlog my_audit_log` — when your log table has a
> different name.

## 16. Complete schema combining multiple features

A realistic schema that combines several features: prefix, audit columns, APEX, rowversion, FK constraints, check constraints, annotations, REST, and a duality view.

**Input:**

```expresql
customers {DESCRIPTION 'Registered customers'}
  full_name  vc200 /nn {DESCRIPTION 'Legal full name'}
  email      vc200 /nn /unique /lower
  country    vc2
  tier       /check STANDARD,GOLD,PLATINUM /nn /default STANDARD

orders /rest /auditcols /rowversion
  customer_id /fk customers /nn
  status      /check OPEN,PROCESSING,SHIPPED,DELIVERED,CANCELLED /nn
  total       num(12,2) /nn
  notes       clob

order_items
  order_id   /fk orders /nn
  product_id /fk products /nn
  quantity   num /nn
  unit_price num(10,2) /nn

view customer_orders customers orders

# settings = {
#   prefix:    "shop_",
#   auditcols: yes,
#   apex:      yes,
#   rowversion: no,
#   drop:      no,
#   db:        "23c",
#   semantics: CHAR
# }
```

**Key generated DDL highlights:**

```sql
-- customers: annotation generates COMMENT ON
create table shop_customers (
    id          number generated by default on null as identity
                constraint shop_customers_id_pk primary key,

                annotations (DESCRIPTION 'Legal full name'),

                    constraint shop_orders_id_pk primary key,
    customer_id     number not null
                    constraint shop_orders_customer_id_fk
                    references shop_customers,
    status          varchar2(4000 char) not null

-- Join view

```

## 17. Shared-schema multi-tenancy with `tenantid: yes`

The `tenantid: yes` setting implements the shared-schema (discriminator) multi-tenancy pattern. ExpreSQL automatically wires the schema for tenant isolation, leaving only optional hardening steps for the developer.

**Supra-tenant vs tenant tables**

Tables marked `/notenantid` are shared across all tenants (lookup data, tenant master). All other tables receive tenant-scoped DDL.

**Input:**

```expresql
subscription_plans /notenantid    -- supra-tenant lookup: shared, no TENANT_ID
  code  vc20 /nn /pk
  name  vc100 /nn
  price num(10,2) /nn

tenants /notenantid               -- master tenant table: supra-tenant
  name      vc200 /nn
  plan_code /fk subscription_plans /nn

customers                         -- tenant table: gets TENANT_ID NOT NULL automatically
  full_name vc200 /nn
  email     vc200 /nn /unique     -- scoped unique: becomes (tenant_id, email)
  country   vc3

orders                            -- tenant table
  customer_id /fk customers /nn  -- composite FK generated automatically
  status      /check OPEN,SHIPPED,CLOSED /nn /default OPEN
  total       num(14,2) /nn

order_lines                       -- tenant table
  order_id   /fk orders /nn /cascade
  sku        vc50 /nn
  qty        num /nn
  unit_price num(10,2) /nn

# settings = { prefix: "app_", tenantid: yes, auditcols: yes, db: "23c" }
```

**Key DDL generated:**

```sql
-- supra-tenant: no TENANT_ID, no tenant logic
create table app_subscription_plans (
    code   varchar2(20 char) not null constraint app_subscription_plans_code_pk primary key,
    name   varchar2(100 char) not null,
    price  number(10,2) not null
);

create table app_tenants (
    id    number generated by default on null as identity
          constraint app_tenants_id_pk primary key,
    name  varchar2(200 char) not null,
    ...
);

-- tenant table: TENANT_ID NOT NULL injected as second column
create table app_customers (
    id          number ... constraint app_customers_id_pk primary key,
    tenant_id   number not null,           -- ← added by tenantid: yes, NOT NULL by default
    full_name   varchar2(200 char) not null,
    email       varchar2(200 char) not null,
    country     varchar2(3 char),
    ...
);

-- email unique scoped to tenant (not global)
create unique index app_customers_tid_email_uix
    on app_customers (tenant_id, email);

-- FK index: tenant_id as leading column
create index app_customers_i1 on app_customers (tenant_id, customer_id);

-- auto-FK: tenant_id → tenants master table (generated because tenants is in the same script)
alter table app_customers add constraint app_customers_tenant_id_fk
    foreign key (tenant_id) references app_tenants (id);

-- (tenant_id, id) unique on customers: on-demand, prerequisite for the composite FK from orders
create unique index app_customers_tid_id_uix
    on app_customers (tenant_id, id);
alter table app_customers add constraint app_customers_tid_id_uq
    unique (tenant_id, id) using index app_customers_tid_id_uix;

-- composite FK from orders to customers: prevents cross-tenant references at DB level
alter table app_orders add constraint app_orders_customer_id_fk
    foreign key (tenant_id, customer_id)
    references app_customers (tenant_id, id);

-- composite FK with ON DELETE CASCADE (from /cascade on order_lines.order_id)
alter table app_order_lines add constraint app_order_lines_order_id_fk
    foreign key (tenant_id, order_id)
    references app_orders (tenant_id, id) on delete cascade;
```

**What ExpreSQL generates automatically:**

| Feature | How to declare |
|---|---|
| `TENANT_ID NUMBER NOT NULL` on all tenant tables | `tenantid: yes` in settings |
| Nullable `TENANT_ID` (for sample data) | Add `/insert N` to the table |
| Auto-FK `tenant_id → tenants(id)` | Have a `tenants` table in the same script |
| Auto-FK to a custom-named master table | `tenantref: "workspaces"` in settings |
| Composite FK `(tenant_id, fk_col) → target(tenant_id, id)` | Any `/fk` between tenant tables |
| `ON DELETE CASCADE` on composite FK | Add `/cascade` to the FK column |
| `(tenant_id, id)` unique on target table | Generated on-demand with FK above |
| `(tenant_id, col)` unique from `/unique` | Add `/unique` to the column |
| `(tenant_id, col)` index from `/idx` | Add `/idx` to the column |
| Supra-tenant table (no TENANT_ID) | Add `/notenantid` to the table |
| Simple FK to supra-tenant table | Automatic when target is `/notenantid` |

**Remaining manual steps** (only when needed):

```sql
-- Only for tables with /insert N (tenant_id is nullable there):
update app_orders set tenant_id = 1 where tenant_id is null;
commit;
alter table app_orders modify tenant_id not null;

-- When the tenants table is in a separate QSQL script (auto-FK not generated):
alter table app_customers add constraint app_customers_tenant_id_fk
    foreign key (tenant_id) references app_tenants (id);
```

See [Multi-Tenant Design](./multitenant-design.md) for the complete enterprise guide: VPD, filtered views, application context, partitioning, and the hardening checklist.

## 18. Schema migration with `toDiff`

**Interactive (editor):** write both schema versions in the same editor separated by `# ---`. The DDL panel switches to migration mode automatically — no extra tabs or buttons needed. Use **⇄ Compare versions** to insert the delimiter.

```expresql
employees
  name vc100 /nn
  email vc200

# ---

employees
  name vc100 /nn
  email vc200 /nn
  phone vc50

departments
  dept_name vc100 /nn
```

The panel shows the migration script, a status bar with counts, and warning bars for destructive operations. See the [Schema Migration](expresql-grammar.md#schema-migration) section of the grammar reference for all details.

**Programmatic:** `toDiff(oldQsql, newQsql)` computes the incremental Oracle DDL migration script between two schema versions. The output is a `DiffResult` containing a runnable SQL script, per-statement metadata, and warnings for destructive or lossy operations.

### Adding a column and a new table

**v1 (old):**

```expresql
employees
  name vc100 /nn
  email vc200
```

**v2 (new):**

```expresql
employees
  name  vc100 /nn
  email vc200 /nn
  phone vc50

departments
  dept_name vc100 /nn
```

**Call:**

```javascript
const result = toDiff(v1, v2);
```

**Generated `result.sql` (key excerpts):**

```sql
-- ============================================================
-- ExpreSQL Migration Script
-- Generated : 2026-05-06T10:00:00.000Z
-- ============================================================
-- ⚠ MANUAL STEPS REQUIRED (statementsRequiringIntervention = 1)
--   [employees.email]
--   Ensure all rows have a non-null value before executing.
-- ============================================================

create table departments (
    id           raw(16)        default sys_guid() not null,
    dept_name    varchar2(100 char) not null,
    --
    constraint departments_pk primary key (id)
);

alter table employees add (phone varchar2(50 char));

-- ⚠ MANUAL INTERVENTION REQUIRED
-- Ensure all rows have a non-null value before executing.
-- alter table employees modify (email not null);
```

**`result.warnings`:**

```json
[
  { "level": "DESTRUCTIVE", "table": "employees", "column": "email",
    "message": "adding NOT NULL on email — requires manual verification",
    "requiresManualIntervention": true }
]
```

**`result.summary`:**

```json
{ "tablesAdded": 1, "tablesDropped": 0, "tablesModified": 1,
  "statementsTotal": 4, "statementsRequiringIntervention": 1, "warningsTotal": 1 }
```

### Dropping a column

```expresql
-- v1
employees
  name  vc100 /nn
  email vc200
  phone vc50

-- v2 (phone removed)
employees
  name  vc100 /nn
  email vc200
```

Generated migration (two-step Oracle pattern):

```sql
alter table employees set unused column phone;
-- [MAINTENANCE] safe to defer to a maintenance window
alter table employees drop unused columns;
```

Warning emitted: `DESTRUCTIVE — column dropped: phone`.

### Rename detection

When exactly one column is dropped and one of the same base type is added, `toDiff` emits a `rename_hint` instead of a destructive DROP + ADD:

```expresql
-- v1: old_email  vc200
-- v2: new_email  vc200  (same base type → suspected rename)
```

```sql
-- alter table employees rename column old_email to new_email;
```

Warning: `INFO — suspected rename: old_email → new_email (verify before applying)`. No destructive DDL is generated; apply the commented statement manually after verifying.

### 23c syntax

Embed `# settings = {"db": "23c"}` in the QSQL strings to get `IF EXISTS` / `IF NOT EXISTS` syntax and skip the PL/SQL idempotency wrappers:

```javascript
const db23 = '\n# settings = {"db": "23c"}';
const result = toDiff(v1 + db23, v2 + db23);
// drop table  if exists employees cascade constraints;
// create index if not exists employees_email_i on employees (email);
```

## 19. Layered TAPI — per-table tier selection

Different tables in the same schema often need different levels of API complexity.
The `/api <tier>` syntax selects the tier per table independently of the global default.

```expresql
-- reference data: app interface only
-- generated: lookup_codes_app
lookup_codes /api lookup
  code  vc20 /nn /unique
  label vc100 /nn

-- business entity with hook stubs but no DAL
-- generated: orders_hks, orders_svc, orders_app
orders /api service+hks
  customer_id num /nn
  total       num(12,2)

-- core entity: full stack without hooks
-- generated: products_dal, products_svc, products_app
products /api full
  name  vc100 /nn
  price num(12,2)

-- top-level entity: full stack with hooks
-- generated: employees_dal, employees_hks, employees_svc, employees_app
employees /api full+hks
  name        vc100 /nn
  email       vc200 /nn /unique
  row_version num   /nn

# settings = { api: layered }
```

Numeric shorthand: `1`=`lookup`, `1h`=`lookup+hks`, `2`=`service`, `2h`=`service+hks`,
`3`=`full`, `3h`=`full+hks`. Both forms are equivalent: `/api 3h` and `/api full+hks`.

## 20. Layered TAPI — degradation (absorbed layers)

When a lower layer is absent, its logic is absorbed as private procedures in the package above it. This lets you start with a leaner tier and upgrade later without changing calling code.

**Service tier (no `_dal` — DML absorbed into `_svc`):**

```expresql
-- _svc body contains private p_get_by_id, p_insert_row, etc.
departments /api service
  name    vc100 /nn
  budget  num(15,2)
```

The generated `departments_svc` body begins with:

```sql
-- private DML (absorbed from absent _dal)

function p_get_by_id (p_id in departments.id%type) return departments%rowtype is ...
procedure p_insert_row (p_row in out nocopy departments%rowtype) is ...
```

**Service+hks tier — `_hks` id type when no `_dal`:**

When `_dal` is absent, the hooks package uses the table anchor type directly:

```sql
-- service+hks: no _dal present
procedure before_delete (p_id in departments.id%type);

-- full+hks: _dal present → use its t_id subtype
procedure before_delete (p_id in departments_dal.t_id);
```

## 22. Layered TAPI — pessimistic locking (`p_lock`)

The `get` procedure (`_app`) and function (`_svc`) accept an optional `p_lock` parameter that controls row-level locking mode. By default (`p_lock => 'none'`), `get` performs a plain SELECT — optimistic concurrency via `row_version` handles conflict detection at write time. Pass `'nowait'` or `'wait'` for pessimistic fetch-for-edit.

**Input:**

```expresql
doctors /api full+hks
  name      vc100 /nn
  specialty vc100
  email     vc200 /nn /unique
  row_version num /nn

# settings = { api: layered }
```

**Three lock modes — `_app`:**

```sql
-- Default: optimistic — no lock, row_version detects lost updates at write time.
doctors_app.get(
    p_id          => :P10_ID,
    p_name        => :P10_NAME,
    p_specialty   => :P10_SPECIALTY,
    p_email       => :P10_EMAIL,
    p_row_version => :P10_ROW_VERSION
);

-- nowait: FOR UPDATE NOWAIT — fails immediately if another session holds the lock.
-- Raises c_err_locked (-20003) [LOCKED].
doctors_app.get(
    p_id          => :P10_ID,
    p_lock        => 'nowait',
    p_name        => :P10_NAME,
    p_specialty   => :P10_SPECIALTY,
    p_email       => :P10_EMAIL,
    p_row_version => :P10_ROW_VERSION
);

-- wait: FOR UPDATE WAIT n — waits up to p_lock_timeout seconds (default 5).
-- Raises c_err_locked (-20003) [LOCKED] if the wait expires.
doctors_app.get(
    p_id           => :P10_ID,
    p_lock         => 'wait',
    p_lock_timeout => 10,          -- wait up to 10 seconds
    p_name         => :P10_NAME,
    p_specialty    => :P10_SPECIALTY,
    p_email        => :P10_EMAIL,
    p_row_version  => :P10_ROW_VERSION
);
```

**REST (`interface: rest`) — ORDS query parameters:**

```http
# Optimistic (default — no query param needed)
GET /ords/schema/doctors/42

# Pessimistic, fail-fast
GET /ords/schema/doctors/42?lock=nowait

# Pessimistic, wait up to 10 seconds
GET /ords/schema/doctors/42?lock=wait&lock_timeout=10
```

**SVC callers (custom service logic):**

```sql
-- check-then-act pattern: lock the row before evaluating a business rule
PROCEDURE transfer_patient (
    p_doctor_id  IN doctors.id%TYPE,
    p_new_specialty IN VARCHAR2
) IS
    l_row doctors%ROWTYPE;
BEGIN
    -- Lock immediately: fail if another session is editing this record
    l_row := doctors_svc.get(p_id => p_doctor_id, p_lock => 'nowait');

    IF l_row.specialty = p_new_specialty THEN
        raise_application_error(-20050, 'Doctor is already in that specialty.');
    END IF;

    -- update_rec acquires OCC check via row_version (always passes after lock_by_id)
    doctors_svc.update_rec(
        p_id          => p_doctor_id,
        p_rec         => doctors_svc.t_rec(name => l_row.name, specialty => p_new_specialty, email => l_row.email),
        p_row_version => l_row.row_version
    );
END transfer_patient;
```

**Error handling — `[LOCKED]` response:**

When `p_lock = 'nowait'` or `p_lock = 'wait'` and the lock cannot be acquired, the stack raises:

```
ORA-20003: [LOCKED] doctors: record locked by another session
```

In APEX, map this in the application Error Handling Function:

```sql
ELSIF p_error.ora_sqlcode = -20003 THEN
    l_result.message := 'This record is currently being edited. Try again in a moment.';
```

In `_rst`, the `WHEN OTHERS` handler already maps `-20003` to HTTP `409 Conflict`.

**Per-table default — `/lockmode` directive:**

If a table is always fetched with pessimistic locking you can set the default once on the table line instead of passing the parameter every time:

```expresql
-- lookup-only table, always locked for 10 seconds while editing
appointment_slots /api lookup /lockmode wait:10
  slot_time timestamp /nn
  available num /nn

# settings = { api: layered }
```

The generated `_app.get` signature becomes:

```sql
procedure get (
    p_id           in  appointment_slots.id%type,
    p_lock         in  varchar2 default 'wait',  -- changed from 'none'
    p_lock_timeout in  number   default 10,       -- changed from 5
    p_slot_time    out appointment_slots.slot_time%type,
    p_available    out appointment_slots.available%type
);
```

Callers still override at runtime — `/lockmode` sets the parameter _default_, not a hard policy.

| Notation | Generated default |
| --- | --- |
| *(absent)* | `p_lock => 'none'`, `p_lock_timeout => 5` |
| `/lockmode nowait` | `p_lock => 'nowait'`, `p_lock_timeout => 5` |
| `/lockmode wait` | `p_lock => 'wait'`, `p_lock_timeout => 5` |
| `/lockmode wait:n` | `p_lock => 'wait'`, `p_lock_timeout => n` |

> **Lock scope**: the lock is held for the duration of the current database transaction and is released on `COMMIT` or `ROLLBACK`. It is **not** held across HTTP requests. For cross-request conflict detection, rely on `row_version` OCC. Use pessimistic locking only within a single transaction (e.g. check-then-act within one SVC procedure, or fetch-for-edit within one APEX page process).

## 23. IBM Db2 — triggers and audit columns

The `/auditcols` directive generates Db2-compatible BEFORE INSERT and BEFORE UPDATE triggers using SQL PL syntax.

**Input:**

```expresql
employees /auditcols
  name    vc100 /nn
  salary  num(12,2)

# settings = {"dialect":"db2","inserts":"no"}
```

**Key generated DDL:**

```sql
--#SET TERMINATOR @

create table employees (
    id          integer not null
                    generated always as identity (start with 1 increment by 1)
                    constraint employees_id_pk primary key,
    name        varchar(100) not null,
    salary      decimal(12,2),
    created_by  varchar(255),
    created     timestamp,
    updated_by  varchar(255),
    updated     timestamp
) @

create or replace trigger employees_biu
before insert on employees
referencing new as n
for each row
begin
    if inserting then
        set n.created_by = current user;
        set n.created    = current timestamp;
    end if;
    set n.updated_by = current user;
    set n.updated    = current timestamp;
end @

create or replace trigger employees_buu
before update on employees
referencing new as n old as o
for each row
begin
    set n.updated_by = current user;
    set n.updated    = current timestamp;
end @
```

Db2 SQL PL trigger conventions:
- `REFERENCING NEW AS n` (insert), `REFERENCING NEW AS n OLD AS o` (update) — no `:new.` / `:old.` Oracle syntax.
- `SET n.col = value` — no `:=` assignment operator.
- `CURRENT TIMESTAMP` and `CURRENT USER` — no `SYSDATE` or `v('APP_USER')`.
- Each object ends with `@` (the custom terminator set at the top).

## 24. IBM Db2 — layered TAPI with schema-based procedures

The `/api` directive generates a layered Table API in Db2 SQL PL.  Because Db2 has no packages, each tier becomes a dedicated **schema** containing `CREATE OR REPLACE PROCEDURE` statements.

**Input:**


**Generated schema layout (`full+hks`):**

| Schema | Contents |
|--------|----------|
| `employees_dal` | `p_get_by_id`, `p_insert_row`, `p_update_row`, `p_delete_row` |
| `employees_hks` | `p_validate`, `p_before_insert`, `p_after_insert`, `p_before_update`, `p_after_update`, `p_before_delete`, `p_after_delete` |

| `employees_rst` | `get`, `ins`, `upd`, `del` — REST interface, returns HTTP status codes |

**Selected generated DDL:**

```sql
end @
```

## 25. Row-level scope with `dimensioncolumns`, `chk_rbac` and `chk_rls`

`tenantid: yes` scopes rows by **equality to a single session-bound value** — the classic one-tenant-per-session SaaS pattern. `dimensioncolumns` covers the different case where scope is **membership in a set** derived from role/group assignment (a caller may legitimately have access to more than one value at once) — e.g. a user with access to several companies, not exactly one. It assumes a `sec_my_scope(dimension_type, code)` view/table already exists, exposing `(dimension_type, code)` for every value the current session is allowed to see.

Unlike `tenant_id`, a dimension column is never synthesized: it must already be a real column on the table (typically an explicit `/fk`) — `dimensioncolumns` only tells the generator which existing columns to treat as scope-bearing, and which dimension type each one represents.

**Input:**

```expresql
companies /api
  name vc200 /nn

invoices /api
  company_id /fk companies /nn
  amount     num /nn

# settings = { api: "layered", dimensioncolumns: { company_id: "COMPANY" } }
```

`companies` has no column configured in the map, so it is generated exactly as a plain layered-API table would be — except every `_hks` package, scoped or not, now also gets a `chk_rbac` hook (see below). `invoices` has a `company_id` column matching the map, so it gets the full treatment.

**A `<table>_rls` view is generated for `invoices`**, once, ahead of every other package for that table (so everything downstream — `invoices_dal`, or the absorbed private DML on tiers without `_dal` — compiles against an existing view, no separate migration step needed):

```sql
create or replace view invoices_rls as
select * from sec_pkg.secured_by_dimension(invoices);
```

`sec_pkg.secured_by_dimension` is a function you provide (typically a `SQL_MACRO(TABLE)` that introspects the table's real columns and filters against your `sec_my_scope` source) — the same one any APEX region or report would read through. ExpreSQL only calls it; it never emits the filter predicate itself.

**Read paths select from that view instead of the base table** (`invoices_dal`):

```sql
function get_by_id (p_id in t_id) return invoices%rowtype is
    l_row invoices%rowtype;
begin
    select * into l_row from invoices_rls where id = p_id;
    return l_row;
end get_by_id;
```

An out-of-scope row never leaves the DAL: `NO_DATA_FOUND` propagates exactly as it would for a genuinely missing id, so a caller cannot tell "does not exist" apart from "not in your scope" — and it's the SAME filter every other reader of `invoices_rls` sees, not a second copy of the logic. `lock_by_id`, `get_all` and `get_by_<unique>` read from the view the same way — and, on tiers without a separate `_dal` (`service`, `lookup`), so does the equivalent absorbed private DML (`p_get_by_id`/`p_get_all`), reading from the same `invoices_rls` view. `insert_row`/`update_row`/`delete_row` do **not** — that's a deliberate difference from `tenantid`, explained below.

**`chk_rbac` and `chk_rls`, in `invoices_hks`:**

```sql
procedure chk_rbac (
    p_operation in varchar2,
    p_row       in invoices%rowtype
) is begin null; end chk_rbac;

procedure chk_rls (p_row in invoices%rowtype) is
begin
    sec_pkg.require_dimension_scope(p_dimension_type => 'COMPANY', p_code => to_char(p_row.company_id));
end chk_rls;
```

`chk_rbac` is generated on **every** table with `api: layered`, `invoices` and `companies` alike — always present, always empty by default (`begin null; end;`), exactly like `validate` and `before_insert` are today. It exists so a permission check, when one is actually needed, has one consistent, always-called place to live; fill it in by hand and it survives regeneration the same way hand-edited `before_*` bodies already do. `chk_rls` is generated **only** for `invoices` — `companies` gets no `chk_rls` at all, not even an empty stub, because there is nothing to check without a configured column. `companies` still gets its own `companies_rls` view though — `select * from companies`, unfiltered — and `companies_dal` reads from it exactly like `invoices_dal` reads from `invoices_rls`: the view exists on every table unconditionally, `chk_rls` only on the ones with something to check. On tiers without `_hks` (`service`, `lookup`), both hooks are absorbed as private `p_chk_rbac`/`p_chk_rls` procedures in whichever package sits above the missing `_hks`, called the same way, in the same order — same degradation rule as every other hook.

**Call order in `invoices_svc`** (identical shape for insert/update/delete, and `close` on `/versioned` tables):

```sql
procedure p_do_create (
    p_rec in  t_rec,
    l_row in out nocopy invoices%rowtype
) is
begin
    l_row.company_id := p_rec.company_id;
    l_row.amount := p_rec.amount;
    invoices_hks.chk_rbac(p_operation => 'insert', p_row => l_row);
    invoices_hks.chk_rls(p_row => l_row);
    invoices_hks.validate(p_operation => 'insert', p_row => l_row);
    invoices_hks.before_insert(p_row => l_row);
    invoices_dal.insert_row(p_row => l_row);
    invoices_hks.after_insert(p_row => l_row);
end p_do_create;
```

`chk_rbac` and `chk_rls` always run *before* `validate`/`before_*` — an unauthorized caller never reaches business-validation logic that might have side effects of its own.

**Why writes don't filter in the WHERE clause, unlike `tenantid`:** `tenantid`'s `update_row`/`delete_row` scope the WHERE clause to the current tenant and let a cross-tenant write silently affect 0 rows. For `dimensioncolumns`, the explicit `chk_rls` check stays authoritative instead — it raises rather than silently doing nothing. This isn't a style preference: it matches already-verified production behavior in the project this setting was built for, where a rejected write is expected to surface as an explicit error, not a quiet no-op.

**`delete_rec` also always fetches the row first now, on every table** — independent of `dimensioncolumns`:

```sql
procedure delete_rec (p_id in invoices.id%type) is
    l_row invoices%rowtype;
begin
    l_row := invoices_dal.get_by_id(p_id => p_id);
    invoices_hks.chk_rbac(p_operation => 'delete', p_row => l_row);
    invoices_hks.chk_rls(p_row => l_row);
    invoices_hks.validate(p_operation => 'delete', p_row => l_row);
    invoices_hks.before_delete(p_id => p_id);
    invoices_dal.delete_row(p_id => p_id);
    invoices_hks.after_delete(p_id => p_id);
end delete_rec;
```

Before this setting, `validate()` never fired on delete at all, on any table — only `before_delete(p_id)` did, which cannot express a row-content-dependent business rule since it never receives the row. The same fix applies to the absorbed `del` path on the `lookup` tier (no `_svc`), which had the identical gap.

**More than one dimension column** on the same table is supported without any special-casing on the write side — `dimensioncolumns: { company_id: "COMPANY", region_id: "REGION" }` generates a `chk_rls` that checks both. On the read side there is still only one `invoices_rls` view — ExpreSQL never emits a per-dimension predicate for it; `secured_by_dimension` itself is expected to introspect the table's columns and AND every dimension it finds, so a multi-dimension table needs no different treatment here than a single-dimension one.

| Setting/hook | Generated when | Behavior on violation |
|---|---|---|
| `chk_rbac` | Always, every table | Empty by default — a no-op until hand-filled |
| `chk_rls` | Only if the table has a configured dimension column | Raises via `sec_pkg.require_dimension_scope` |
| `<table>_rls` view + read paths reading from it | Always, every table (filtered if a dimension column is configured, an unfiltered passthrough otherwise) | Row never returned when out of scope; same `NOT_FOUND` as missing id |
| Write paths reading from `<table>_rls` | Never (unlike `tenantid`'s WHERE-clause enforcement) | N/A — `chk_rls` is authoritative instead |
